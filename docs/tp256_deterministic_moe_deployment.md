# Groq 3 LPX 上 TP=256 确定性 MoE 部署方案

> **场景**：AFD 分离架构下，GPU（Vera Rubin NVL72）负责 Prefill + Decode Attention + KV Cache + 采样/路由，LPX（256×LP30）**只负责 MoE/FFN**。
>
> **本文目标**：给出一个在 Groq 3 LPX 256-LPU 机架上、采用 **TP=256 张量并行**部署 MoE，且**严格保证 LPU 静态确定性**的完整方案。
>
> **配置假设**：Batch = 32；256 个路由专家，每 token 激活 top-8；`top-8 专家选择 + 路由权重 + 专家激活 mask 表`全部由 GPU 计算并下发；FFN 采用标准 Megatron 式 TP：**Gate/Up linear 列切分，Down linear 行切分**。

---

## 一、方案定位：什么是 TP=256

在 LPX 上部署 256 专家 MoE 有多种并行切分方式（EP 专家并行、TP+EP 混合、纯 TP 等）。本方案选择的是**纯 TP、并行度 = 256** 的极端：

```text
TP=256：每一个专家都被张量切分到全部 256 张 LPU 上
        每张 LPU 持有【全部 256 个专家】的 1/256 分片
        每一次 FFN 计算，全部 256 张 LPU 共同参与每一个专家
```

与之对立的另一极端是 **TP=8 托盘内方案**（每个专家的 TP group = 1 个托盘，Down 归约在托盘内 K₈ 单跳完成）。两者的本质区别在于 **Down 行并行归约的落点**——TP=256 需要**全机架集合通信**，TP=8 只需**托盘内单跳**。本文专注 TP=256，第九节给出与 TP=8 的对比。

**为什么 TP=256 在 LPX 上依然可行**（反直觉点）：虽然每个专家在单张 LPU 上只剩 8 列中间维，看似会退化成利用率极低的 skinny GEMM，但 256 个专家的分片可以**拼接成稠密大 GEMM**（见第五节），使单卡计算等价于"一个中间维 2048 的稠密 FFN"，MXM 收缩阵列满载。这是 TP=256 成立的技术根基。

## 二、前提：AFD 职责划分

```text
┌─────────────────────── GPU (Vera Rubin NVL72) ───────────────────────┐
│  Prefill · Decode Attention · KV Cache · 采样                          │
│  ★ Router：计算 top-8 专家 ID + routing_weight + 生成 mask 表          │
│  ★ 下发激活 X[32,7168] 与 mask/weight 表到 LPX                          │
│  ★ 回收 MoE_out[32,7168]，继续下一层 Attention                         │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │  GPU↔LPX C2C 链路
┌───────────────────────────────┴───────────────────────────────────────┐
│                      LPX (256 × LP30)  —— 只做 MoE/FFN                   │
│  无 KV Cache · 无 Attention · 无动态调度                                 │
│  全部 256 LPU 对全部 256 专家做恒定全算 + PAARD AllReduce               │
└─────────────────────────────────────────────────────────────────────────┘
```

关键前提：**路由决策（哪些专家激活）完全在 GPU 侧完成**。LPX 收到的 mask/weight 只是一张 `[32, 256]` 的数值表，它**永远不会改变 LPX 上任何一条指令流或通信路径**——这是确定性的先决条件。

## 三、静态权重布局（编译期固定，全生命周期不变）

标准 Megatron TP 切分（以 DeepSeek-V3 尺寸为例：H=7168，中间维 I=2048）：

```text
Gate/Up 列切分：沿中间维 I=2048 切成 256 份 → 每 LPU 每专家 8 列
Down    行切分：沿输入维 I=2048 切成 256 份 → 每 LPU 每专家 8 行
```

在 **LPU_i（i = 0..255）** 上，把 256 个专家的分片**拼接**存放：

```text
Wgate_stk[7168, 2048]   ← 拼接: [ W_gate[0][:, i*8:(i+1)*8] | ... | W_gate[255][:, i*8:(i+1)*8] ]
Wup_stk  [7168, 2048]   ← 同理，256 个专家的 up 列分片横向拼接
Wdown_stk[2048, 7168]   ← 纵向堆叠: 256 个专家的 down 行分片 [8,7168] 依次堆叠

参数量 = 3 × 7168 × 2048 = 44.0 M params
FP8 存储 = 44 MB / LPU   （恰好 = 1 个完整专家的等效体量，因为 256 专家 ÷ TP256 = 1）
占用 = 44 MB / 500 MB SRAM ≈ 9%   ✓ 余量充足
```

> **拼接顺序（专家 0→255）在编译期固定**，这样 mask/weight 表 `[32,256]` 的第 e 列就精确对应 `Wgate_stk` 的第 `e*8:(e+1)*8` 列块，运行时无需任何查找或重排。

## 四、端到端确定性流水线

每个 Decode Step 执行**完全相同**的四阶段流水线，指令流逐位一致：

```text
① 入口 (GPU → LPX)                                    [ 决策 3-B ]
   ├─ GPU 送 32 份 X[32,7168] BF16 = 448KB 到各托盘的入口 LPU（每托盘 1 份）
   ├─ routing_weight×mask 表 [32,256] BF16 = 16KB 随行下发到同一入口 LPU
   └─ 托盘内 K₈ 单跳广播 → 同托盘 8 个 LPU 各持完整 X 与 mask/weight（~300ns）
        [ GPU 出口只发 32 份，而非 256 份，带宽降 8× ]

② 单卡计算 (3 个满载稠密 GEMM)                          [ 决策 5-A ]
   G  = X[32,7168] @ Wgate_stk[7168,2048]  → [32,2048]
   U  = X[32,7168] @ Wup_stk[7168,2048]    → [32,2048]
   A  = SiLU(G) ⊙ U                         → [32,2048]        (逐元素)
   WA[t, e*8:(e+1)*8] = w[t,e]·mask[t,e] · A[t, e*8:(e+1)*8]   (逐专家块数值缩放 = 折叠)
   local_partial = WA[32,2048] @ Wdown_stk[2048,7168] → [32,7168]
        [ 256 专家恒定全算；未激活专家块被 mask 乘 0，但仍参与 GEMM ]

③ 归约 (PAARD 4-phase AllReduce, [32,7168] = 448KB)     [ 决策 4-B ]
   Phase 1  托盘内 Reduce-Scatter (K₈, 1 跳)
   Phase 2  跨托盘 Ring-Reduce-Scatter (31 步, 每步 1 跳)
   Phase 3  跨托盘 Ring-All-Gather   (31 步, 每步 1 跳)
   Phase 4  托盘内 All-Gather (K₈, 1 跳)
   → 256 LPU 人人持完整 MoE_out[32,7168]

④ 出口 (LPX → GPU)
   固定 LPU_0 回传 MoE_out[32,7168] BF16 = 448KB → GPU
   GPU 继续下一层 Attention
```

### 4.1 折叠恒等式（第②③步为何能塌缩成 1 次 AllReduce）

```text
MoE_out[t] = Σ_{e ∈ top8(t)}  w[t,e] · FFN_e(t)
           = Σ_{e=0..255}     w[t,e]·mask[t,e] · Σ_{i=0..255} partial_{e,i}[t]   (Down 行并行)
           = Σ_{i=0..255} ( Σ_{e=0..255} w[t,e]·mask[t,e] · partial_{e,i}[t] )   ← 交换求和次序
                          └────────── local_partial_i[t]，LPU_i 本地可独立算出 ──────────┘
```

**关键**：把 routing_weight×mask 的加权折叠**放在 AllReduce 之前**（在每个 LPU 本地完成），256 个专家的贡献先在本地坍缩成 1 份 `[32,7168]` 的 `local_partial`，于是全机架**只需要 1 次** `[32,7168]` 的 AllReduce，而不是 256 次。

## 五、单卡计算详解：为什么拼接 GEMM 让 TP=256 可行

### 5.1 朴素做法（错误示范）

逐个专家计算，每个专家在本 LPU 只有 8 列：

```text
for e in 0..255:
    g_e = X[32,7168] @ Wgate_e_shard[7168, 8]  → [32, 8]    N=8
```

Groq MXM 是 320×320 收缩阵列，`N=8` 只用了阵列 **2.5%** 宽度；256 次这种 skinny GEMM = MXM 利用率灾难，且指令开销 ×256。

### 5.2 拼接做法（本方案采用）

因为 256 个专家的 gate 分片都乘同一个 `X`，可以横向拼成一个大权重，一次 GEMM 算出全部：

```text
G = X[32,7168] @ Wgate_stk[7168, 2048] → [32, 2048]     N=2048, MXM 满载
U = X[32,7168] @ Wup_stk[7168, 2048]   → [32, 2048]
A = SiLU(G) ⊙ U                         → [32, 2048]
```

`A` 的第 `e*8:(e+1)*8` 列块 = 专家 e 的中间激活分片。折叠在此插入（逐块数值缩放）：

```text
WA[t, e*8:(e+1)*8] = w[t,e] · mask[t,e] · A[t, e*8:(e+1)*8]
```

Down 也拼接（纵向堆叠 256 个 `[8,7168]` 分片），一次 GEMM 完成加权求和：

```text
local_partial = WA[32,2048] @ Wdown_stk[2048,7168] → [32,7168]
              = Σ_{e} WA_e[32,8] @ Wdown_e[8,7168]
              = Σ_{e} w[t,e]·mask[t,e] · (act_e @ Wdown_e)     ← 正是折叠后的本地贡献
```

**结论**：TP=256 的单卡计算等价于"一个中间维 2048 的稠密 FFN + 两个 GEMM 之间的逐块加权"。3 个 GEMM 全部 MXM 满载，mask/weight 只是插在中间的**编译期固定位置的运行时数值**。这是整个方案的技术根基。

### 5.3 加权位置的选择：Down 之前 vs Down 之后

本方案把 `w[t,e]·mask[t,e]` 加在**中间激活 A 上、Down GEMM 之前**（位置①）。一个自然的疑问是：能否像常规 MoE 那样，把加权放在 **Down linear 之后**？

由于 `w[t,e]` 是一个 **per-(token,expert) 的标量**、Down 是**线性**算子，加权可以穿过 Down、穿过行并行部分和、穿过 AllReduce，三者**数学等价**：

```text
w·(A_e @ Wdown_e) = (w·A_e) @ Wdown_e            ← 穿过 Down GEMM
Σ_i w·partial_{e,i} = w·Σ_i partial_{e,i}         ← 穿过行并行 AllReduce
```

于是有三个可能的加权位置：

```text
① Down 之前（本方案）：w 加在中间激活 A[32,2048] 上
② Down 之后、AllReduce 之前：w 加在每专家的 Down 部分和 partial_{e,i}[32,7168] 上
③ Down 之后、AllReduce 之后：w 加在每专家完整 down_e[32,7168] 上（= §九 决策2 已否决的 256 次 AllReduce）
```

**这不是正确性问题，纯粹是工程实现问题**。下表对比位置① vs 位置②（③见 §九 决策2）：

| 维度 | 位置①（Down 前·本方案） | 位置②（Down 后·AllReduce 前） | 胜者 |
|------|------------------------|-------------------------------|------|
| 数学结果 | `w·(A@Wdown)` | `(w·A)@Wdown` 分离后加权 | 等价（仅差 FP 累加顺序） |
| 确定性 | 全算 + 固定顺序 | 全算 + 固定顺序 | 相同 |
| Down GEMM 形态 | **1 个 K=2048 拼接 GEMM** | **256 个 K=8 skinny GEMM** | ①（MXM 满载 vs 2.5%） |
| 指令/调度长度 | 3 个 GEMM | 256+ 个 GEMM | ① |
| FP8 精度（本方案 W8A16，A=BF16） | 无下溢 | 无优势（前提不满足） | ①（②无收益） |
| 中间显存 | 448 KB | 448KB（累加）/ 114MB（materialize） | ① |

**关键差异（求和发生在哪）**：

```text
位置①：w 已提前乘进 WA → 256 专家可在一个 K=2048 的 Down GEMM 内【直接求和坍缩】
位置②：必须对每专家 Down 输出【分别】乘 w → 求和前不能坍缩
        → 被迫拆成 256 个 K=8 skinny GEMM（MXM 收缩阵列深 320，利用率仅 8/320=2.5%）
        → 正是 §5.2 描述的 skinny GEMM 坑
```

**位置②唯一的理论翻盘点是 FP8 下溢**：若中间激活 A 为 FP8，位置①的 `w·A`（w 是很小的 softmax 权重）再量化回 FP8 可能下溢损失精度，而位置②在宽精度输出上缩放更安全。**但本方案是 W8A16（权重 FP8、激活 BF16），中间激活 A 在 BF16 流里**，`w·A` 在 BF16 完成、动态范围远宽于 FP8，无下溢——位置②的精度前提根本不满足。（即便扩展到 W8A8 场景，也可把 `w[t,e]` 折进 Down GEMM 输入的 per-block scale factor 中和下溢，不值得为此付 256 个 skinny GEMM。）

**结论**：`w[t,e]` 是标量、Down 是线性——加权放 Down 前后数学等价、确定性相同，差异纯在工程。**位置①靠"提前乘 w"让 256 专家在一个 K=2048 大 GEMM 内求和坍缩，MXM 满载**；位置②被迫退化为 256 个 skinny GEMM，且其唯一的 FP8 精度优势在本方案 W8A16 下不成立。**因此位置①严格占优。**

> **通用原则**：*逐元素的标量缩放，尽量提前折进"能被后续 GEMM 沿收缩维吸收"的位置*——既省一次遍历，又保住 GEMM 融合。

## 六、归约详解：PAARD 4-phase AllReduce

`local_partial[32,7168]` = 448KB，需在 256 个 LPU 间求和。LPX 的 QuadFour 拓扑是 Dragonfly 变体（32 托盘 = 32 组，每托盘 8 LPU 经 K₈ 全连接），采用面向 Dragonfly 的 PAARD 算法（详见 `PAARD_analysis.md`）。

```text
数据分片：[32,7168] ÷ 8(托盘内) ÷ 32(托盘间) = [32,28] = 1.75KB/切片

Phase 1  托盘内 Reduce-Scatter（K₈，铜缆，1 跳）
         每 LPU 把 448KB 切成 8 份，向同托盘 7 邻居各发对应分片并累加
         → 每 LPU 持 [32,896] 的托盘内归约

Phase 2  跨托盘 Ring-Reduce-Scatter（QSFP，31 步，每步 1 跳）
         把 [32,896] 再切 32 份，沿 32 托盘 Ring 推进 31 步
         → 每 LPU 持 [32,28] 的【完整全局归约切片】

Phase 3  跨托盘 Ring-All-Gather（31 步逆向）
         把 [32,28] 沿 Ring 广播回 32 托盘 → 每 LPU 持 [32,896]

Phase 4  托盘内 All-Gather（K₈，1 跳）
         组内广播 → 每 LPU 持完整 [32,7168]
```

> **为何是 4 phase 而非 PAARD 原论文的 6 步**：QuadFour 每托盘仅 8 个直连邻居（非 Palmtree 全对全），无法执行"32 托盘单步全局交换"，故用 Ring-RS/AG（31 步）替代原 Step 2/5，并因 Ring 天然让每个 LPU 同步持有自己的切片而省去原 Step 3/4 的"代表节点分发"。总数据量不变（2N/LPU），每步仍 1 跳。详见 `PAARD_analysis.md §7.4`。

> **为何切 Hidden dim 而非 Token dim**：AllReduce 的语义是对 `local_partial` 沿 LPU 维求和，每个 LPU 都持有全部 32 个 token 的部分和，切分的是被求和的 hidden 维（7168），使每步 Ring 传输量最小、且切片边界编译期固定。

## 七、确定性保证：三重锁定

LPU 的静态确定性要求编译器在**编译期**固定所有指令流、C2C 路径、每步传输时刻。本方案通过三重锁定满足：

### 7.1 计算确定
```text
256 个专家【恒定全算】，3 个 GEMM 的形状永远是
  [32,7168]×[7168,2048]、[32,7168]×[7168,2048]、[32,2048]×[2048,7168]
→ 与 top-8 路由结果无关，每个 decode step 指令流【逐条相同】
→ 未激活专家不是"被跳过"，而是"被 mask 乘 0 后照常参与 GEMM"
```

### 7.2 通信确定
```text
入口 K₈ 广播、Phase1-4 的 PAARD、出口 LPU_0 回传——
拓扑、每条 C2C 链路、每步发送/接收时刻全部编译期静态调度
→ 无硬件仲裁、无动态路由决策、Plesiosynchronous 时钟对齐
```

### 7.3 数值确定
```text
运行时输入 X / routing_weight / mask 仅作为 numeric 数据流经固定管线
唯一随路由变化的 = WA 中被乘 0 的专家块的【数值】，
不改变任何一条指令、任何一次通信、任何一个时刻
→ TruePoint 逐位可复现（bit-exact reproducible）
```

### 7.4 确定性证明（反证）

> **命题**：若任何步骤"按 mask 跳过未激活专家"，确定性即被摧毁。
>
> **证明**：假设跳过 mask=0 的专家块，则第②步 GEMM 的有效列数 = `8 × (当前 step 激活的不同专家数)`，该值随每个 token 的 top-8 路由结果变化 → GEMM 形状 data-dependent → 编译器无法在编译期确定指令时长与 MEM 访问模式 → 静态调度失效，退化为 GPU 式运行时动态调度。∎

**因此"全算 + 数值 mask"是 LPU 静态确定性的唯一相容路径。** 用 97% 的"白算"换取指令流的绝对静态——这正是 LPU 相对 GPU 的根本取舍。

## 八、量化分析

### 8.1 存储（每 LPU）
| 项 | 大小 |
|----|------|
| 权重（FP8，拼接后） | 44 MB |
| 激活 X[32,7168] BF16 | 448 KB |
| mask/weight 表 [32,256] | 16 KB |
| 中间量 G/U/A[32,2048] ×3 | ~384 KB |
| AllReduce 缓冲 [32,7168] | 448 KB |
| **合计** | **≈ 45.3 MB / 500 MB (9%)** |

### 8.2 计算（每 LPU 每 step）
```text
GEMM MAC = 32×7168×2048 (Gate) + 同 (Up) + 32×2048×7168 (Down)
         ≈ 1.41 G MAC = 2.82 GFLOP
LP30 单卡 FP8 算力 = 315 PFLOPS / 256 ≈ 1.23 PFLOPS
计算下界 ≈ 2.82G / 1.23P ≈ 2.3 μs
```

### 8.3 访存 vs 计算（B=32 是否够摊薄权重）
```text
权重读取 = 44 MB / 150 TB/s ≈ 0.29 μs  ≪  计算 2.3 μs
→ 计算受限（compute-bound），B=32 已充分摊薄权重加载。B=1 时为访存受限。
```

### 8.4 通信延迟（AllReduce，估算）
```text
以每跳 C2C 延迟 α ≈ 300ns、小消息 α 主导估算：
  Phase 1 (K₈, 1 跳)          ≈ 0.3 μs
  Phase 2 (Ring-RS, 31 步)    ≈ 31 × 0.3 ≈ 9.3 μs
  Phase 3 (Ring-AG, 31 步)    ≈ 9.3 μs
  Phase 4 (K₈, 1 跳)          ≈ 0.3 μs
  ─────────────────────────────────────
  完整 AllReduce（决策 4-B）  ≈ 19 μs（未计流水线重叠）
```
> Ring 步间可流水线重叠，实际显著低于此上界；且 448KB 小消息下带宽项可忽略。**归约（~19μs）是延迟主导项，远超计算（2.3μs）**——这直接引出第九节的决策 4 备选。

### 8.5 利用率
```text
专家计算有效率 = 激活专家 / 全部专家 = 8/256 = 3.1%   （"白算"占 97%）
MXM 阵列利用率 = 高（拼接 GEMM N=2048/7168 满载）    ← 关键：低有效率 ≠ 低 MXM 利用率
```

## 九、决策记录与备选方案

本方案在 6 个决策点上做了选择，记录如下（含备选，便于后续对比）：

| 决策 | 选择 | 备选 | 影响 |
|------|------|------|------|
| 1. 两方案定义 | TP=256 全机架 | TP=8 托盘内 | 见下方对比 |
| 2. mask/weight 折叠位置 | **AllReduce 之前** | 之后 | 256 次 AllReduce → 1 次（决定性） |
| 3. 入口广播 | **GPU→32 托盘入口 + K₈ 广播** | GPU 直播 256 份 | 出口带宽 114MB → 14MB |
| 4. 归约深度 | **完整 AllReduce (4 phase)** | 只做 RS (2 phase) + GPU 拼接 | 见下方权衡 |
| 5. 单卡计算组织 | **拼接 3 稠密 GEMM** | 逐专家 256 skinny GEMM | MXM 利用率 2.5% → 满载 |
| 6. 是否跳过未激活专家 | **不跳过（全算+数值 mask）** | 动态跳过 | 确定性成立 vs 摧毁确定性 |

### 9.1 决策 4 的权衡：完整 AllReduce vs 仅 Reduce-Scatter

本方案选了**完整 AllReduce（B）**。但 AFD 场景下 GPU 天然是汇聚点，存在一个更优备选：

```text
备选 A（仅 Reduce-Scatter + GPU 拼接）：
  只做 Phase 1+2 → 每 LPU 持 [32,28] 完整归约分片
  256 个 LPU 各把自己的 [32,28]=1.75KB 直接发回 GPU
  GPU 按固定 LPU 编号 concat 256 份 → [32,7168]
  ┌─────────────────────────────────────────────┐
  │ LPX 内部通信砍半（省掉 Phase 3/4 的 AllGather）│
  │ 归约延迟 ~19μs → ~9.6μs                        │
  │ 出口 448KB → 896KB（可接受）                   │
  └─────────────────────────────────────────────┘
```

> **建议**：若以最小化端到端 Decode 延迟为首要目标，决策 4 应改为 A。当前选 B 的理由是出口带宽更省、且 LPX 输出语义更简单（单点全量回传）。二者确定性等价。

### 9.2 TP=256 vs TP=8 托盘内方案

| 维度 | TP=256（本方案） | TP=8 托盘内 |
|------|-----------------|-------------|
| Down 归约落点 | 全机架 PAARD（~19μs 或 ~9.6μs） | 托盘内 K₈ 单跳（~0.3μs） |
| 专家驻留 | 每 LPU 持全部 256 专家分片 | 每托盘持 8 专家，8 专家/托盘 × 32 = 256 |
| 单卡权重 | 44 MB | 44 MB（8 专家 × 5.5MB） |
| 单卡 GEMM 中间维 | 2048（拼接） | 2048（完整专家） |
| 归约延迟 | **高（全机架集合通信主导）** | **极低（单跳）** |
| 有效算力利用 | 3.1% | 3.1%（同样全算） |
| 复杂度 | 需 PAARD 全机架 | 归约不出托盘 |
| **适用** | 追求超大专家/超大模型的极致切分 | **追求最低 Decode 延迟的首选** |

> **重要结论**：在本文的 B=32 / 256 专家配置下，**TP=8 托盘内方案的归约延迟低 1~2 个数量级**（单跳 vs 全机架），是低延迟 Decode 的更优选择。TP=256 的价值在于当单专家过大、必须跨全机架切分权重时，它提供了一条**确定性可行**的路径。两种方案的确定性保证机制完全一致（全算 + 数值 mask + 静态拓扑）。

---

## 十、总结

本方案给出了 Groq 3 LPX 上 **TP=256 部署 256 专家 top-8 MoE** 的完整确定性设计：

1. **静态布局**：每 LPU 拼接存放全部 256 专家的列/行分片（FP8 44MB，占 9% SRAM）。
2. **计算塌缩**：256 专家拼成 3 个 MXM 满载稠密 GEMM，mask/weight 在两 GEMM 间做逐块数值折叠，把 256 次 AllReduce 塌缩为 1 次。
3. **确定性三重锁定**：计算恒定全算（指令流同构）+ 通信静态拓扑（PAARD/K₈ 编译期固定）+ 数值参数化（TruePoint 逐位可复现）。
4. **唯一相容路径**："全算 + 数值 mask、绝不按路由跳过"是 LPU 静态确定性的充要工程约束。

**代价与取舍**：97% 专家计算为"白算"（但 MXM 满载，B=32 下计算仅 2.3μs）；归约延迟（~9.6~19μs）是端到端主导项。若以最低延迟为目标，**TP=8 托盘内方案**（归约单跳）优于 TP=256；TP=256 的定位是**超大专家必须全机架切分权重时的确定性可行方案**。
